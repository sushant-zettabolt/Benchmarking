### Things to know when reading results

- **Compare within a run, not across runs.** With identical settings, the long-prompt run
  came out a median 11% (up to 28%) below the main sweep, for both engines. Pinning checked
  out and nothing else was using 160-191; the cause is unknown. Within a run the spread is
  under 1%. Use each variant's own `-base` / `-base-end` as the reference.
- `--load-mode mlock` fails under the pod's 8 MB `ulimit -l` (a warning in the server log),
  so llama.cpp runs effectively use mmap.
- The pod only allows memory node 5 (`Mems_allowed_list: 5`), so interleaving memory across
  nodes cannot be tested here.

## Checking on it

From the workstation, in `/proj/aigstaff/sohroy/Benchmarking` (same NFS checkout as the pod,
nothing to log in to):

```bash
python3 scripts/turin_status.py             # every tuning run: progress, current test, eta, failures
python3 scripts/turin_status.py out/<run>   # any other run
tail -20 sweep-tune.log                     # the driver script's own log
```

A run showing `running` while the status script warns "no event for 30+ min" has probably
died. Check its process (pid from the status output) as root; no user login needed:

```bash
/usr/local/bin/kubectl exec turin-xcovoid0021-pod-5 -n zendnn -- ps -o pid,etime,args -p <pid>
```

In tcsh, kubectl needs `setenv KUBECONFIG /proj/zendnn/k8/dev-kubeconfig.yaml` first; without it
you get "connection refused" on localhost:8080.

## Getting into the pod

```tcsh
setenv KUBECONFIG /proj/zendnn/k8/dev-kubeconfig.yaml
/usr/local/bin/kubectl exec -it turin-xcovoid0021-pod-5 -n zendnn -- login sohroy
cd /proj/aigstaff/sohroy/Benchmarking && . .venv/bin/activate
```

If the pod was recreated, all its processes are gone and the sweep has stopped. Its `run.json`
will still say `running`. The `login` step recreates the `sohroy` account in the new pod; until
someone runs it, `runuser -l sohroy` fails with "user does not exist". Check the core range
again (`taskset -pc $$`, expected `160-191`) before resuming.

## If a run stopped

In the pod, as sohroy:

```bash
python3 scripts/turin_status.py                           # which run, and why (status/error)
llmbench sweep cleanup out/turin-tune-<name> --dry-run    # servers it left behind; rerun without --dry-run
scripts/run_turin_tune.sh resume                          # finished trials are kept
```

Run `resume` detached, like the original:
`setsid nohup scripts/run_turin_tune.sh resume > sweep-tune.log 2>&1 < /dev/null &`.
Before resuming you may change only timeouts, `settle_s`, `continue_on_error` or the objective.
Any other edit changes the plan fingerprint and `--resume` refuses it. To stop a run cleanly,
`kill <pid>` once and wait for teardown. Never kill processes by name; other people use these
hosts.

## Getting results to Windows

Each run's `report.md`, `report.html`, `report.csv` and `best.json` are in its `out/` directory.
Zip what you need on the workstation, then pull it from PowerShell:

```bash
zip -r turin-tune-results.zip out/turin-tune-llamacpp out/turin-tune-vllm
```
```powershell
scp sohroy@xcosdaeg571:/proj/aigstaff/sohroy/Benchmarking/turin-tune-results.zip $HOME\Downloads\
```

The long-prompt results are already zipped: `turin-qwen36-longctx-2026-09-28.zip`.
